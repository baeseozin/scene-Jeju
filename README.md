# scene-Jeju — 분위기 메이커

사용자의 현재 위치에서 제주 촬영 장소까지 도착하는 시각을 계산하고, 그 시각의 날씨·태양 위치·장소 특성·콘셉트를 합쳐 촬영 적합도를 `좋음 / 괜찮음 / 시간 조정 추천`으로 안내하는 해커톤 MVP입니다.

기본값은 API 키 없이 실행되는 `mock` 모드입니다. 카카오 REST API 키가 있으면 제주 장소 검색과 자동차 실제 경로 조회를 시도하고, 기상청 키와 `APP_MODE=auto` 또는 `real`을 설정하면 실제 예보를 사용합니다. 외부 API 조회에 실패해도 `auto` 모드에서는 mock 또는 거리 기반 추정값으로 전환됩니다.

발표용 전체 계산식, 데이터 출처, AI 포즈 추천 구조, 한계와 심사위원 예상 질문은 [`TECHNICAL_DETAILS.md`](./TECHNICAL_DETAILS.md)에 정리되어 있습니다.

## 구현 기능

- 장소명 검색: 카카오 로컬 검색 결과를 선택하면 이름·좌표·장소 유형 자동 입력
- 지도 선택: 카카오 JavaScript 키가 있으면 실제 지도, 없으면 클릭 가능한 제주 간편 지도 제공
- 지도에서 지점을 누르면 주변 장소명·주소·좌표·장소 유형 자동 입력
- 장소 유형 수동 보정: 해변·숲길·도심·실내
- 콘셉트 6개: 청량한·자연스러운·노을 실루엣·포근한·무드있는·반짝이는
- 촬영 결과 선택: 사진 또는 15초 영상
- 이동수단 선택: 자동차·대중교통·도보
- 자동차는 카카오모빌리티 실제 경로 우선, 대중교통·도보는 거리 기반 예상 시간
- 출발 시각 + 이동시간으로 도착 예상 시각 계산
- 지금 출발 또는 48시간 안의 출발 날짜·시간을 사용자가 직접 선택
- 모든 콘셉트를 도착 직후부터 12시간 뒤까지 1시간 간격으로 비교해 저녁 조건까지 확인
- 도착 직후가 이미 `좋음`이면 바로 촬영을 추천하고, 그렇지 않을 때 `좋음 → 괜찮음 → 시간 조정 추천` 순으로 더 나은 시각 탐색
- 추천 시각의 날씨·태양·점수·촬영 방향·가이드를 한 기준으로 표시
- 6개 콘셉트마다 분석 결과 화면의 배경색과 강조색 변경
- 기상청 초단기예보와 단기예보 자동 전환
- 강수량·풍속·하늘상태(`맑음 / 구름 많음 / 흐림`) 반영
- 제주 관광 빅데이터 플랫폼의 `제주 지역별 관광지 도착` TOP 10을 장소명과 매칭해 최근 방문 경향 기반 혼잡 가능성 표시
- 관광 빅데이터가 조회되지 않아도 공식 데이터 저장본으로 데모를 계속하고, 실시간 혼잡도가 아님을 화면에 명시
- `pvlib` 기반 태양 고도·방위각 계산
- `pvlib` 청천 일사량과 기상청 하늘상태를 결합한 예상 일사량(GHI·DNI·DHI) 계산
- 장소별 빛 균형 위험 분석: 해변 수면 반사, 숲 얼룩 그림자, 도심 유리·노면 반사, 실내 창문 역광
- 날씨 40% + 빛 45% + 장소 15%의 설명 가능한 점수
- 장소 유형과 콘셉트에 맞는 쉬운 촬영 위치 문장 제공
- 스마트폰 1× 카메라 기준으로 인물과 주요 배경, 촬영자와 인물 사이의 시작 거리 안내
- 촬영 후 예상되는 색감·명암과 얼굴·하늘의 노출 실패 가능성 안내
- 사진 구도 가이드와 15초 영상 촬영 가이드 분리
- 영상 클립 최대 4개를 브라우저 안에서 나누기·자르기·순서 변경·삭제·음소거하고 배속·색감·밝기·확대·화면 위치·문구·전환 효과를 적용해 최대 15초 세로 MP4 또는 WebM으로 편집·저장
- 영상 원본 소리 유지, 사진 최대 4장은 9:16 JPG 콜라주로 저장
- 웹 카메라 화면에 콘셉트별 반투명 인물 포즈 실루엣을 겹쳐 사진 또는 최대 15초 영상을 직접 촬영
- 전신(머리부터 발끝)·상반신(머리부터 허리) 촬영 범위를 사용자가 선택
- 컨셉을 최우선으로 장소 유형·사진/영상·촬영 범위를 보조 조건으로 사용해 서로 다른 포즈 3개 추천
- 포즈마다 몸·손·시선·촬영자 거리·추천 이유를 쉬운 문장으로 제공
- `OPENAI_API_KEY`가 있으면 Responses API의 구조화된 출력으로 포즈를 생성하고, 없거나 호출 실패 시 컨셉별 기본 포즈 라이브러리로 전환
- 추천 포즈를 고른 뒤 시원하게·걷는 순간·옆모습·차분하게 유형의 반투명 실루엣, 가이드 투명도, 전·후면 카메라 전환 사용
- 사용자의 현재 자세를 인식하거나 포즈 일치율을 채점하지 않음
- 포즈 가이드는 촬영 위치 확인용으로만 표시하고 실제 사진·영상에는 합성하지 않음
- 분석 기록 최대 10개를 브라우저에 저장
- 모바일 공유 시 분석 결과 이미지 카드를 첨부하고, 미지원 환경에서는 이미지 다운로드와 문구 복사로 대체
- 390px 모바일 화면 대응

## 빠른 실행

### 1. 환경 설정

프로젝트 루트에서 환경 파일을 만듭니다.

```bash
cp .env.example .env
```

키 없이 실행하려면 아래 상태로 둡니다.

```dotenv
APP_MODE=mock
KMA_SERVICE_KEY=
KAKAO_REST_API_KEY=
OPENAI_API_KEY=
OPENAI_POSE_MODEL=gpt-5.6-luna
VITE_KAKAO_JAVASCRIPT_KEY=
FRONTEND_ORIGIN=http://localhost:5178
```

실제 데이터를 사용하려면 필요한 키를 입력합니다.

```dotenv
# 키가 있으면 실제 예보, 실패하면 mock으로 전환
APP_MODE=auto
KMA_SERVICE_KEY=공공데이터포털_일반인증키

# 장소 검색과 자동차 길찾기에 사용하는 서버용 REST API 키
KAKAO_REST_API_KEY=카카오디벨로퍼스_REST_API키

# 실제 카카오 지도 화면에 사용하는 프론트용 JavaScript 키
VITE_KAKAO_JAVASCRIPT_KEY=카카오디벨로퍼스_JavaScript키

# 컨셉 맞춤 포즈 3개를 생성하는 서버용 키
OPENAI_API_KEY=OpenAI_API키
# 간단한 구조화 추천이므로 비용·응답속도를 고려한 기본값
OPENAI_POSE_MODEL=gpt-5.6-luna

FRONTEND_ORIGIN=http://localhost:5178
```

`KAKAO_REST_API_KEY`와 `VITE_KAKAO_JAVASCRIPT_KEY`는 서로 다른 키입니다. JavaScript 키를 쓰려면 카카오 디벨로퍼스에서 `http://localhost:5178`을 Web 플랫폼 도메인으로 등록해야 합니다. 키가 없으면 장소 검색은 사용할 수 없지만, 좌표 직접 입력과 간편 지도는 사용할 수 있습니다.

### 2. 백엔드

Python 3.11 이상이 필요합니다.

```bash
cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8008
```

API 문서: [http://localhost:8008/docs](http://localhost:8008/docs)

### 3. 프론트엔드

새 터미널에서 실행합니다.

```bash
cd frontend
npm install
npm run dev
```

브라우저에서 [http://localhost:5178](http://localhost:5178)을 엽니다.

기본 `npm run dev`는 휴대폰 시연 중 코드 파일 변경 감지 때문에 페이지가 반복 새로고침되는 일을 막기 위해 HMR을 끈 안정 모드입니다. 코드를 고칠 때마다 자동 반영되는 데스크톱 개발 모드가 필요하면 `npm run dev:hot`을 사용합니다. 안정 모드에서는 코드를 수정한 뒤 브라우저를 한 번 직접 새로고침해야 합니다.

환경값을 변경하면 백엔드와 프론트 개발 서버를 모두 다시 시작해야 합니다.

## 데이터 사용 방식

### 전체 분석 순서

`POST /api/analyze` 한 번이 다음 순서로 처리됩니다.

1. 사용자의 현재 좌표, 촬영 장소, 콘셉트, 촬영 종류, 이동수단, 출발 시각을 받습니다.
2. 자동차는 카카오모빌리티 경로를 우선 조회하고, 나머지 이동수단 또는 API 실패 시 거리 기반 식으로 이동시간을 계산합니다.
3. `도착 예상 시각 = 출발 시각 + 이동시간`으로 계산합니다.
4. 도착 직후부터 12시간 뒤까지 총 13개 시각을 1시간 간격으로 만듭니다.
5. 각 시각에 대해 기상청 예보, `pvlib` 태양 위치·일사량, 장소 유형별 빛 위험을 계산합니다.
6. 각 시각의 날씨·빛·장소 점수와 강제 판정 조건을 적용합니다.
7. 도착 직후가 이미 `좋음`이면 그 시각을 선택합니다. 그렇지 않으면 `좋음 > 괜찮음 > 시간 조정 추천`을 먼저 비교하고, 같은 상태의 최고점에서 5점 이내인 후보 중 가장 빠른 시각을 선택합니다.
8. 선택된 시각의 촬영 방향, 거리, 동작, 예상 결과와 실패 가능성을 쉬운 문장으로 만듭니다.
9. 관광지 이름이 제주 관광 빅데이터 TOP 10과 일치하면 최근 방문 경향과 사람을 피할 촬영 팁을 추가합니다. 이 값은 촬영 적합도 총점에는 넣지 않습니다.

핵심 시간 계산식은 다음과 같습니다.

```text
arrival_time = departure_time + travel_minutes
target_time[i] = arrival_time + i hours,  i = 0 ... 12
status_priority: 좋음=2, 괜찮음=1, 시간 조정 추천=0
if arrival_status == 좋음: best = arrival_time
else: best = earliest(candidate within 5 points of the highest score in the best status)
```

| 제주 관광 빅데이터 | `제주 지역별 관광지 도착`, 공개 차트 응답 | 월, 관광지명, 차량 도착 건수, TOP 10 순위 | 최근 방문 경향과 군중 회피 안내 | 없음 |

| `pvlib` | `get_solarposition`, `simplified_solis` | 겉보기 태양 높이, 태양 방향, 맑은 하늘 GHI·DNI·DHI | 시간대별 빛 점수와 장소별 빛 위험 | 없음, 서버 내부 계산 |
| 브라우저 위치 | Geolocation API | 사용자의 위도·경도 | 출발 위치 | HTTPS 또는 `localhost` 권한 |
| 브라우저 카메라 | `getUserMedia` | 전·후면 카메라 스트림, 영상 모드에서는 마이크 | 반투명 포즈 가이드 촬영 | HTTPS 또는 `localhost` 권한 |
| 브라우저 편집·저장 | Canvas, `captureStream`, `MediaRecorder`, `localStorage`, Web Share API | 사용자가 선택한 로컬 미디어와 편집 설정 | 9:16 결과 생성, 기록 저장, 공유 | 없음 |

`pvlib`는 외부 서버에서 관측 데이터를 받아오는 API가 아닙니다. 좌표와 timezone이 포함된 시각을 입력해 태양 위치를 계산하는 Python 라이브러리입니다. 예상 일사량 역시 현장 센서값이 아니라 청천 모델과 기상청 하늘상태를 조합한 추정값입니다.

제주 관광 빅데이터는 공식 공개 화면의 차트 응답을 읽습니다. 플랫폼이 별도의 안정적인 공개 Open API 규격을 보장한 형태가 아니므로, 화면 구조나 응답 형식이 바뀌면 실시간 조회가 실패할 수 있습니다. 그래서 공식 데이터 저장본을 함께 두었습니다.

### 프로젝트 내부 기준 데이터

사용자는 제주 장소를 직접 검색할 수 있지만, 다음 3개 장소는 방향과 설명을 미리 검토한 데모용 기준 장소입니다.

| 장소 | 유형 | 위도·경도 | 미리 등록한 주요 배경 방향 |
| --- | --- | --- | --- |
| 협재해수욕장 | 해변 | `33.3941, 126.2397` | 비양도가 보이는 서쪽 `275°` |
| 사려니숲길 | 숲길 | `33.4087, 126.6265` | 삼나무 길이 깊어지는 북동쪽 `25°` |
| 도두동 무지개해안도로 | 도심 | `33.5058, 126.4685` | 바다가 열리는 북서쪽 `330°` |

카카오에서 받은 장소명과 카테고리는 다음 키워드 순서로 유형을 추론합니다.

1. `해수욕장·해변·해안·바다·포구·항구`가 있으면 해변
2. `숲·오름·수목원·휴양림·산·공원·정원·산책로·폭포`가 있으면 숲길
3. `박물관·미술관·전시·카페·호텔·리조트·실내`가 있으면 실내
4. 어느 조건에도 해당하지 않으면 도심

이 분류는 자연어 모델이 아니라 키워드 규칙이라 오분류될 수 있으므로 사용자가 해변·숲길·도심·실내 중 하나로 직접 수정할 수 있습니다.

### 이동시간

| 이동수단 | 계산 방식 | 결과 표시 |
| --- | --- | --- |
| 자동차 | REST 키가 있으면 카카오모빌리티 자동차 길찾기 API의 거리·소요시간 | 카카오 실제 자동차 경로 |
| 자동차 대체 경로 | API 권한·네트워크 오류 시 Haversine 거리, 제주 도로 우회율, 평균 속도 | 거리 기반 예상값 |
| 대중교통 | 거리, 평균 운행속도, 정류장 이동·배차 대기 15분 | 거리 기반 예상값 |
| 도보 | 직선거리, 보행 우회율, 평균 보행속도 4.5km/h | 거리 기반 예상값 |

이 MVP에서 실제 경로로 연결한 것은 카카오모빌리티 자동차 길찾기뿐입니다. 대중교통과 도보는 실시간 경로가 아니며 결과 화면에서도 실제값과 예상값을 구분합니다.

현재 구현에서 사용하는 거리·시간 계산식은 다음과 같습니다.

```text
# 먼저 두 위·경도 사이의 대권거리 d를 Haversine 공식으로 계산
a = sin²(Δlat/2) + cos(lat1) × cos(lat2) × sin²(Δlon/2)
d = 2 × 6371.0088 × asin(√a)                       # km

# 자동차 API 대체값
road_distance = d × 1.23                           # 제주 도로 우회율
speed = 38 km/h if road_distance < 35 km else 46 km/h
car_minutes = round(road_distance / speed × 60 + 7) # 진출입 여유 7분

# 도보
walk_distance = d × 1.16
walk_minutes = ceil(walk_distance / 4.5 × 60)

# 대중교통
transit_distance = d × 1.28
transit_minutes = ceil(transit_distance / 27 × 60 + 15) # 정류장 이동·배차 대기
```

우회율과 평균속도는 해커톤 MVP용 경험적 상수이며 실제 교통량·도로 통제·버스 배차를 반영한 통계모형은 아닙니다. 참고로 현재 카카오맵 문서에는 별도의 대중교통·도보 경로 API도 안내되어 있지만, 이 저장소에는 아직 연동하지 않았습니다. 따라서 화면의 대중교통·도보 결과는 계속 `예상값`으로 표시합니다.

### 날씨

- 도착 시각이 초단기예보 범위 안이면 `getUltraSrtFcst`의 `RN1`, `WSD`, `SKY`를 사용합니다.
- 범위를 벗어나면 `getVilageFcst`의 `PCP`, `WSD`, `SKY`를 사용합니다.
- `APP_MODE=mock`: 항상 결정론적 데모 날씨
- `APP_MODE=auto`: 실제 예보 우선, 실패하면 mock
- `APP_MODE=real`: 실제 예보 실패 시 API 오류 반환
- 화면의 `LIVE WEATHER / DEMO WEATHER` 표시는 실제 분석 응답의 데이터 출처를 기준으로 바뀝니다.

정확한 구름 퍼센트는 계산하지 않습니다. 기상청 `SKY` 값에 맞춰 `맑음 / 구름 많음 / 흐림`만 사용합니다.

기상청 위·경도 입력은 바로 사용할 수 없어서 기상청 Lambert Conformal Conic 격자 `(nx, ny)`로 변환합니다. 초단기예보는 매시 30분 발표 자료가 API에 반영되는 시간을 고려해 **45분 이후에만 현재 시각 자료**를 사용하고, 그 전에는 한 시간 전 발표 자료를 사용합니다. 단기예보는 `02·05·08·11·14·17·20·23시` 중 API 반영 여유 15분을 확보한 가장 최근 발표를 선택합니다.

| 코드 | 의미 | 코드 처리 |
| --- | --- | --- |
| `RN1` | 초단기예보 1시간 강수량 | `강수없음`은 `0`, 문자열에서 수치를 추출해 mm로 사용 |
| `PCP` | 단기예보 1시간 강수량 | `강수없음`은 `0`, 문자열에서 수치를 추출해 mm로 사용 |
| `WSD` | 풍속 | m/s 실수로 변환 |
| `SKY=1` | 맑음 | `맑음`으로 매핑 |
| `SKY=3` | 구름 많음 | `구름 많음`으로 매핑 |

각 API 응답을 `예보 날짜 + 예보 시각`으로 묶고 `강수·풍속·하늘상태`가 모두 있는 시각만 후보로 사용합니다. 도착 시각 이후의 첫 예보를 선택하고, 이후 예보가 없으면 전체 후보 중 도착 시각과 가장 가까운 값을 사용합니다. 따라서 화면에 30분 단위 시각이 보이더라도 날씨 원자료를 30분 단위로 예측한 것은 아닙니다.

### 태양과 촬영 방향

태양 고도와 방위각은 timezone이 포함된 도착 예상 시각으로 `pvlib`에서 계산합니다. 콘셉트별로 순광·옆빛·역광·반사광 관계가 되도록 촬영자가 설 위치를 계산합니다. 화면에는 각도보다 다음과 같은 행동 문장을 먼저 보여줍니다.

> 바다가 인물 뒤에 넓게 보이도록 자리를 잡고, 촬영자는 태양을 등진 채 인물을 바라보세요.

실내 장소는 비·강풍·일몰 때문에 자동으로 비추천되지 않으며, 창문과 밝은 조명 배치를 중심으로 평가·안내합니다.

### 예상 일사량과 장소별 빛 위험

`pvlib`로 맑은 하늘에서의 일사량을 계산한 뒤, 기상청 `SKY`의 `맑음 / 구름 많음 / 흐림` 단계에 따라 감쇠하여 예상 일사량을 만듭니다. 화면의 `W/m²` 값은 현장 센서의 실측값이 아니라 도착 예상 시각의 촬영 조건을 비교하기 위한 추정값입니다.

```text
# 맑음
GHI = clear_GHI
DNI = clear_DNI
DHI = clear_DHI

# 구름 많음
GHI = clear_GHI × 0.65
DNI = clear_DNI × 0.45
DHI = max(0, GHI - DNI × sin(solar_elevation))

# 흐림
GHI = clear_GHI × 0.28
DNI = clear_DNI × 0.08
DHI = max(0, GHI - DNI × sin(solar_elevation))
```

- `GHI`: 수평면에 들어오는 전체 빛의 양
- `DNI`: 태양에서 직접 들어오는 빛의 세기
- `DHI`: 구름과 대기에서 퍼져 들어오는 빛의 양
- `clear_*`: `pvlib.simplified_solis`가 계산한 맑은 하늘 기준값

`SKY`는 정확한 구름 두께나 구름 퍼센트가 아니므로 `0.65·0.45·0.28·0.08`은 관측 구름량을 복원한 값이 아니라 MVP의 보수적인 감쇠계수입니다.

| 콘셉트 | 목표 느낌 | 주요 빛 조건 | 결과 화면 색 |
| --- | --- | --- | --- |
| 청량한 | 파란 하늘과 선명한 제주 | 강한 일사량·맑음·높은 태양 | 스카이블루 |
| 자연스러운 | 편안하고 부드러운 자연광 | 중간 일사량·약간의 구름 | 그린 |
| 노을 실루엣 | 감성적인 역광과 인물 윤곽 | 일몰 전후·낮은 태양 | 오렌지·코럴 |
| 포근한 | 부드럽고 따뜻한 인물 사진 | 구름이 있는 확산광 | 크림·베이지 |
| 무드있는 | 흐리고 차분한 영화 같은 느낌 | 구름 많음·낮은 일사량 | 블루그레이 |

촬영 방향은 콘셉트가 요구하는 태양과 카메라의 상대관계로 계산합니다.

```text
recommended_camera_azimuth = (solar_azimuth - target_sun_offset) mod 360
angle_difference = abs((solar_azimuth - target_sun_azimuth + 180) mod 360 - 180)
direction_score = clamp(100 - max(0, angle_difference - 18) × 0.95)
```

사용자 검색 장소는 건물·길·해안선의 실제 방향을 모르므로 방향 점수를 `75점`의 중립값으로 둡니다. 미리 등록된 3개 예시 장소만 협재 `275°`, 사려니 `25°`, 도두 `330°`의 권장 배경 방향과 태양 방향을 비교합니다. 화면에서는 이 숫자를 그대로 보여주지 않고 “촬영자가 두세 걸음 옆으로 이동하세요” 같은 행동 문장으로 바꿉니다.

| 장소 유형 | 분석하는 대표적인 빛 문제 | 사용자 안내 예시 |
| --- | --- | --- |
| 해변 | 수면 반사·역광·강한 직사광 | 태양에서 20~30° 옆으로 이동 |
| 숲길 | 나뭇잎 틈의 직사광이 만드는 얼룩 그림자 | 한두 걸음 옆의 빛이 고른 그늘로 이동 |
| 도심 | 유리·노면 반사, 강한 햇빛과 건물 그늘의 명암 차 | 반사 방향을 피해 옆으로 이동하거나 그늘 안쪽 선택 |
| 실내 | 창문 역광과 실내외 명암 차 | 창문을 인물 뒤가 아닌 얼굴의 45° 옆에 배치 |

결과에는 `빛 위험 낮음 / 보통 / 높음`과 원인을 함께 표시합니다. 건물·창문·나무의 실제 위치를 3차원으로 측정하는 기능은 아니므로, 장소 유형에서 흔히 발생하는 문제를 미리 경고하고 현장에서 쉽게 수정할 행동을 제안하는 지표로 사용합니다.

촬영 가이드의 거리값은 스마트폰 1× 카메라로 인물과 풍경을 함께 담기 위한 시작 기준입니다. 현장의 통행로, 안전선, 장애물과 렌즈 화각에 따라 사용자가 조금씩 이동해 조정해야 하며 실제 공간을 측량한 결과는 아닙니다.

## 점수 산정

모든 하위 점수와 최종 점수는 반올림한 뒤 `0~100` 사이로 제한합니다. 범위 점수는 권장 범위 안이면 100점이고, 범위 밖으로 멀어질수록 정해진 감소율만큼 선형으로 낮아집니다.

```text
clamp(x) = round(max(0, min(100, x)))

range_score(value, min, max, falloff):
  min ≤ value ≤ max 이면 100
  아니면 clamp(100 - 권장 범위까지의 거리 × falloff)
```

### 1. 날씨 점수

```text
rain_score = 100                                      if rain ≤ concept.max_rain
rain_score = clamp(75 - (rain - max_rain) × 55)      otherwise

comfortable_wind = concept.max_wind × 0.65
wind_score = 100                                      if wind ≤ comfortable_wind
wind_score = clamp(
  100 - (wind - comfortable_wind) / (max_wind × 0.85) × 100
)                                                     otherwise

sky_score = 100                                       if SKY ∈ preferred_skies
sky_score = 42                                        otherwise

weather_score = clamp(
  rain_score × 0.45 + wind_score × 0.25 + sky_score × 0.30
)
```

실내는 비·바람의 직접 영향이 작기 때문에 강수와 바람 하위점수를 최소 90점, 하늘 하위점수를 최소 75점으로 보정한 뒤 같은 식을 적용합니다.

### 2. 빛 점수

```text
elevation_score = range_score(
  solar_elevation, concept.min_elevation, concept.max_elevation, 6.5
)

irradiance_score = range_score(GHI, concept.min_GHI, concept.max_GHI, 0.16)
```

- 등록 장소: `빛 = 높이 40% + 일사량 32% + 방향 28%`
- 사용자 검색 장소: 현장 구조를 모르므로 방향을 75점으로 두고 `빛 = 높이 45% + 일사량 40% + 방향 15%`
- 실내: 방향을 100점으로 두고 `빛 = 높이 35% + 일사량 30% + 실내 기본값 35점`
- 일사량 계산값이 0이면 일사량 점수 대신 햇빛 높이 점수를 사용합니다.
- 장소별 빛 위험이 `보통`이면 빛 점수에 `0.94`, `높음`이면 야외 `0.82`, 실내 `0.90`을 곱합니다.
- 노을의 수면 역광과 반짝이는 콘셉트의 반사광은 의도된 효과라서 위 위험 감점을 생략하지만 얼굴 노출 경고는 표시합니다.
- `무드있는` 야외 촬영은 일몰 후 어두운 바다·수평선·인물 윤곽도 의도된 결과로 봅니다. 일반 콘셉트의 야간 강제 제한을 적용하지 않고 밤의 깊이에 따라 빛 점수를 단계화하며, 야간 모드와 휴대폰 고정 안내를 함께 제공합니다. 가로등·건물 조명 데이터는 없으므로 얼굴이 밝게 나온다는 의미는 아닙니다.

### 3. 장소 점수

| 콘셉트 | 해변 | 숲길 | 도심 | 실내 |
| --- | ---: | ---: | ---: | ---: |
| 청량한 | 100 | 90 | 95 | 75 |
| 자연스러운 | 95 | 100 | 90 | 78 |
| 노을 실루엣 | 100 | 75 | 95 | 55 |
| 포근한 | 82 | 95 | 88 | 100 |
| 무드있는 | 85 | 100 | 95 | 90 |
| 반짝이는 | 100 | 65 | 90 | 55 |

### 4. 총점과 상태

```text
total = clamp(weather_score × 0.40 + light_score × 0.45 + place_score × 0.15)
```

| 총점 | 판정 |
| --- | --- |
| 70점 이상 | 좋음 |
| 50~69점 | 괜찮음 |
| 49점 이하 | 시간 조정 추천 |

API 내부의 기존 상태 코드는 저장된 분석 기록과의 호환성을 위해 각각 `가능 / 보통 / 비추천`을 유지하지만, 사용자 화면과 공유 이미지에는 위의 긍정적인 표현을 사용합니다. 따라서 74점은 `좋음`으로 표시됩니다.

가중평균만 사용하면 폭우처럼 치명적인 조건이 다른 만점에 가려질 수 있으므로 다음 상한을 적용합니다. 실내에는 야외용 강제 규칙을 적용하지 않습니다.

- 야외에서 햇빛 높이가 `-6°` 미만이면 `시간 조정 추천`이며, 밤이 깊어질수록 상한이 `47점`에서 더 낮아집니다. 단, 밤 자체를 결과물로 쓰는 `무드있는` 콘셉트는 예외입니다.
- 심한 비 기준은 `max(2.0mm, 콘셉트 허용 강수 + 1.5mm)`입니다. 이를 넘으면 `시간 조정 추천`이며 초과량에 따라 `46점`보다 더 낮아집니다.
- 바람이 콘셉트 최대값보다 `3m/s` 이상 강하면 `시간 조정 추천`이며 초과량에 따라 `46점`보다 더 낮아집니다.
- 햇빛 높이가 권장 범위에서 `20°`보다 더 벗어나면 `시간 조정 추천`입니다.
- 허용 강수량이나 최대 바람을 조금만 넘긴 경우, 햇빛 높이가 권장 범위에서 `8°`보다 더 벗어난 경우에는 결과를 최대 `괜찮음`으로 제한합니다.
- 의도된 노을·반사 효과가 아닌데 장소별 빛 위험이 높으면 결과를 최대 `괜찮음`으로 제한합니다.

예전처럼 모든 비추천을 단순히 `49점`으로 잘라 표시하지 않습니다. 야간 깊이, 강수 초과량, 바람 초과량, 햇빛 높이 차이에 따라 비추천 상한을 다르게 낮춰 서로 다른 위험 정도가 점수에 나타나도록 구현했습니다.

## 사진·영상 편집과 저장

### 컨셉 기반 AI 포즈 추천

이 기능의 목적은 **현재 자세를 분석하거나 잘했는지 채점하는 것이 아니라**, 사용자가 고른 분위기에 맞는 포즈 자체를 촬영 전에 제안하는 것입니다. 입력 우선순위는 `컨셉 > 장소 유형 > 사진/영상 > 전신/상반신`입니다. 카메라 영상, 얼굴, 신체 관절, 체형 정보는 추천 입력에 포함하지 않습니다.

프론트는 분석 결과가 바뀌면 다음 요청을 한 번 보냅니다.

```http
POST /api/pose-recommendations
Content-Type: application/json

{
  "concept_id": "sunset",
  "place_type": "beach",
  "capture_mode": "photo",
  "framing": "upper_body"
}
```

`framing`은 `full_body` 또는 `upper_body`입니다. 백엔드는 `CONCEPTS`에서 컨셉 이름과 설명을 검증한 뒤, `OPENAI_API_KEY`가 있으면 OpenAI Responses API를 호출합니다. 기본 모델은 단순한 구조화 추천의 비용과 지연시간을 고려해 `gpt-5.6-luna`로 설정했으며 `OPENAI_POSE_MODEL`로 바꿀 수 있습니다. 요청은 상태를 저장할 필요가 없어 `store: false`, 복잡한 추론이 필요하지 않아 `reasoning.effort: none`, 장황함을 줄이기 위해 `text.verbosity: low`를 사용합니다.

출력은 자유 문장이 아니라 `json_schema` 구조화 출력으로 제한합니다. 포즈는 정확히 3개이며 각 항목은 다음 필드를 반드시 가집니다.

| 필드 | 의미 |
| --- | --- |
| `guide_type` | 반투명 실루엣에 연결할 `open / walk / side / soft` 중 하나 |
| `name`, `one_line` | 사용자가 처음 보는 포즈 이름과 한 줄 행동 |
| `body` | 발, 체중, 상체 방향 등 몸 전체 동작 |
| `hands` | 손 위치와 힘을 주지 않는 방법 |
| `gaze` | 렌즈·배경 중 어디를 볼지 |
| `camera` | 촬영자와 인물 사이의 시작 거리와 구도 |
| `why` | 선택한 컨셉에 이 포즈가 어울리는 이유 |

모델 프롬프트에는 다음 제한을 명시합니다.

1. 현재 사람의 자세를 분석하거나 점수를 매기지 않는다.
2. 컨셉을 최우선으로, 장소 유형과 사진/영상은 보조 조건으로 쓴다.
3. 서로 다른 포즈 3개를 추천한다.
4. 전문 촬영 용어 대신 바로 따라 할 수 있는 한국어를 쓴다.
5. 신체 비율·외모·아름다움을 평가하지 않는다.
6. 전신은 발끝이 잘리지 않게, 상반신은 머리부터 허리와 손이 화면 안에 들어오게 안내한다.

API 키가 없거나 네트워크·요금·응답 형식 문제로 호출이 실패해도 촬영 흐름을 막지 않습니다. 같은 응답 구조를 가진 컨셉별 기본 라이브러리에서 3개를 반환하며 화면에는 `AI POSE DIRECTOR` 대신 `POSE GUIDE`라고 표시합니다. 따라서 **실제 AI 응답과 fallback을 화면과 API의 `source` 값으로 구분**할 수 있습니다. fallback까지 AI라고 부르지 않는 것이 발표 방어의 핵심입니다.

같은 브라우저 탭에서 `컨셉 + 장소 유형 + 사진/영상 + 전신/상반신` 조합이 같으면 `sessionStorage`의 추천을 재사용합니다. 사용자가 화면을 다시 열 때마다 같은 AI 요청을 반복해 비용과 대기시간이 늘어나는 것을 막기 위한 세션 단위 캐시이며, 탭을 닫으면 사라집니다.

추천 결과에서 하나를 고르면 `guide_type`에 맞는 반투명 SVG 실루엣을 카메라 위에 표시합니다. 전신은 머리부터 발끝이 들어오는 전체 실루엣, 상반신은 머리부터 허리 구간을 확대해 표시합니다. 실루엣에는 눈·코·입이 있지만 단순한 가이드 그래픽이며, 사용자의 얼굴을 인식한 결과가 아닙니다. 카메라 영상은 서버나 OpenAI로 전송하지 않고, 가이드도 촬영 파일에 합성하지 않습니다.

### 브라우저 편집과 저장 방식

- 영상 파일은 서버로 전송하지 않고 사용자의 브라우저 안에서만 처리합니다.
- `포즈 가이드로 찍기`는 `getUserMedia`로 카메라 미리보기 위에 반투명 SVG 실루엣을 표시합니다. 촬영 결과는 기존 사진 콜라주 또는 릴스 편집 목록으로 바로 들어갑니다.
- 웹 카메라는 브라우저 보안 정책상 `HTTPS` 또는 컴퓨터의 `localhost`에서만 동작합니다. 휴대폰에서 `http://192.168.x.x`로 접속하면 포즈 오버레이 카메라는 차단될 수 있으며, 이때는 `폰 기본 카메라` 버튼을 사용할 수 있습니다.
- 휴대폰 Safari의 메모리 사용을 줄이기 위해 카메라는 `720×1280`을 우선 요청합니다. 이전의 실시간 관절 인식 모델과 프레임별 React 갱신은 제거했습니다.
- `npm run dev`는 휴대폰 시연 안정성을 위해 Vite HMR을 끕니다. 개발 중 자동 반영이 필요할 때만 `npm run dev:hot`을 사용합니다.
- 카메라·마이크 권한은 촬영 버튼을 누른 뒤 사용자에게 요청하며, 스트림과 파일은 서버에 업로드하지 않습니다.
- 카메라 미리보기는 9:16 영역을 꽉 채우기 위해 현재 `object-fit: cover`를 사용합니다. 휴대폰이 4:3 스트림을 반환하면 좌우가 잘려 실제 줌이 아니어도 확대되어 보일 수 있습니다. 저장 사진도 1080×1920의 중앙 9:16 영역으로 자릅니다. 전체 화각을 보이게 하려면 `contain` 방식과 여백 처리로 바꿔야 합니다.
- 파일 하나는 150MB, 선택한 파일 전체는 300MB까지 받습니다.
- 최대 4개 클립을 가운데에서 나누고 시작·끝 구간, 순서, 음소거 여부를 직접 정할 수 있습니다.
- 클립별 `0.5× / 1× / 1.5× / 2×` 배속, 원본·따뜻·청량·필름·흑백 색감, 밝기, 확대, 좌우·상하 화면 위치를 조절할 수 있습니다.
- 영상 문구와 상단·중앙·하단 위치를 정하고, 클립 사이는 빠른 컷 또는 부드러운 페이드를 선택할 수 있습니다.
- 선택한 구간을 순서대로 연결하고 편집 후 재생시간 기준 최대 15초까지 9:16 영상으로 내보냅니다.
- Safari처럼 MP4 녹화를 지원하는 브라우저는 MP4, Chrome 계열은 WebM으로 저장합니다.
- 실제 영상 편집에 약 15초가 걸리며 브라우저가 지원하는 코덱에 따라 저장 형식이 달라집니다.
- 사진 모드에서는 최대 4장을 1080×1920 JPG 콜라주로 저장합니다.
- 분석 기록은 서버 DB가 아니라 브라우저 `localStorage`에 최대 10개 저장됩니다.
- 공유는 결과 점수·추천 시각·날씨·촬영 방향·촬영 순서가 담긴 PNG 카드를 만듭니다. Web Share API 파일 공유를 우선 사용하고, 미지원 환경에서는 이미지를 다운로드하고 문구를 복사합니다.

## API

- `GET /api/catalog`: 예시 장소와 콘셉트

- `POST /api/pose-recommendations`: 컨셉·전신/상반신 맞춤 포즈 3개와 몸·손·시선·촬영 거리 추천
- `POST /api/analyze`: 이동시간, 시간대별 날씨·빛, 최적 시각, 촬영 가이드 분석

## 사실대로 말해야 하는 제한

- 대중교통과 도보는 실제 경로·배차 정보가 아닌 예상값입니다.
- `SKY`는 정확한 구름 퍼센트가 아니라 3단계 하늘상태입니다.
- 예상 일사량은 `pvlib`의 청천 모델과 `SKY` 단계별 감쇠계수로 계산한 추정값이며 현장 실측값이 아닙니다.
- 장소 유형은 카카오 장소명과 카테고리의 키워드로 추론하므로 사용자가 수정할 수 있게 했습니다.
- 임의 장소의 촬영법과 빛 위험은 장소 유형과 콘셉트별 모델입니다. 현장 장애물, 수관 밀도, 건물·창문 방향을 카메라로 인식하거나 3차원으로 측정한 결과는 아닙니다.
- `OPENAI_API_KEY`가 없거나 호출에 실패한 경우에는 생성형 AI가 아니라 사람이 작성한 컨셉별 기본 포즈 라이브러리를 사용하며 화면에 fallback임을 구분해 표시합니다.
- AI 추천도 전문 포토그래퍼의 현장 판단이나 사용자 취향 학습 결과가 아닙니다. 현재 입력은 컨셉·장소 유형·사진/영상·전신/상반신뿐이며, 개인화·체형 분석·포즈 정확도 평가는 하지 않습니다.
- 영상 편집은 장면 의미를 AI가 자동으로 이해하는 방식이 아니라, 사용자가 클립과 효과를 직접 정하는 브라우저 기반 편집입니다. 전환은 빠른 컷과 페이드만 지원하며 배경음악·스티커·키프레임 편집은 포함하지 않습니다.
- 영상의 MP4/WebM 형식은 브라우저의 `MediaRecorder` 지원 코덱에 따라 달라집니다.
- 실제 기상청 데이터는 별도 서비스 키가 있어야 검증할 수 있습니다.
